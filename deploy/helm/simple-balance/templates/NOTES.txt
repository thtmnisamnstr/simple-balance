Simple Balance {{ .Chart.AppVersion }} is installed as {{ .Release.Name }} in namespace {{ .Release.Namespace }}.

Three workloads: {{ $serverName }} (API and MCP), {{ $frontendName }} (browser
bundle and the proxy in front of the API), {{ $schedulerName }} (recurrences).

1. Watch them come up. The API and the scheduler both run the migrations under
   an advisory lock on first start, so the first rollout takes as long as the
   migrations do and readiness stays closed until they finish:

     kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ $serverName }}
     kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ $frontendName }}
     kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ $schedulerName }}

   A pod stuck not-ready is nearly always the database: the role in DATABASE_URL
   needs CREATEDB if the database it names does not exist yet.

     kubectl -n {{ .Release.Namespace }} logs deploy/{{ $serverName }}

{{ if .Values.ingress.enabled -}}
2. Point DNS at your ingress controller for {{ .Values.ingress.host }}, and make
   sure the {{ if .Values.ingress.tls.issuer }}Issuer {{ .Values.ingress.tls.issuer }}{{ else if .Values.ingress.tls.clusterIssuer }}ClusterIssuer {{ .Values.ingress.tls.clusterIssuer }}{{ else }}TLS secret{{ end }} exists. Then:

     kubectl -n {{ .Release.Namespace }} get ingress {{ $fullname }}
{{- if .Values.ingress.tls.enabled }}
     kubectl -n {{ .Release.Namespace }} get certificate

   The site answers on https://{{ .Values.ingress.host }}/ once the certificate
   is ready.
{{- else }}

   The site answers on http://{{ .Values.ingress.host }}/.
{{- end }}
{{- else -}}
2. No Ingress is enabled, so nothing outside the cluster reaches this yet. To
   look at it:

     kubectl -n {{ .Release.Namespace }} port-forward svc/{{ $frontendName }} 8080:{{ .Values.frontend.service.port }}

   Sign-in cookies are issued for {{ .Values.config.appBaseUrl }}, so a
   port-forward on another origin will not keep you signed in. Set
   config.appBaseUrl to whatever origin people actually reach before using this
   for real.
{{- end }}

3. Claim the first account at {{ .Values.config.appBaseUrl }}/.
{{ if and .Values.secret.create .Values.secret.setupToken }}
   The one-time code is the SETUP_TOKEN you put in secret.setupToken.
{{ else }}
   The one-time code was generated once for this deployment, so every API pod
   prints the same one and any pod's log has it:

     kubectl -n {{ .Release.Namespace }} logs deploy/{{ $serverName }} | grep -i setup
{{ end }}
   Then set config.allowedEmails to say who else may register. Left empty,
   nobody but that first account can.

{{- if and .Values.ingress.enabled (ne $appHost .Values.ingress.host) }}

WARNING: config.appBaseUrl names {{ $appHost }} but the Ingress answers on
{{ .Values.ingress.host }}. The API sets the cookies the browser reads and
compares every write against this origin, so the two have to be the same host.
Fix config.appBaseUrl unless something else in front is doing the translating.
{{- end }}

{{- if and .Values.config.trustProxy .Values.ingress.enabled (eq .Values.frontend.trustedProxyCidr "127.0.0.1") }}

WARNING: every sign-in attempt in this cluster counts against one allowance.
The frontend's nginx tells the API which address a request came from, and behind
an ingress that terminates TLS that address is the ingress — the same value for
every visitor. With config.trustProxy on and frontend.trustedProxyCidr left at
its off position, four wrong passwords from anywhere lock everyone else out.

Set frontend.trustedProxyCidr to the pod CIDR your ingress controller runs in:

  --set frontend.trustedProxyCidr=<ingress controller pod CIDR>

Name the controller's range and nothing wider. This decides whose word is taken
for a visitor's address, so a range that includes callers lets a caller choose
their own.
{{- end }}

Database connections. This release peaks at {{ $serverPeak }} API and {{ $schedulerPeak }} scheduler
replicas, each holding {{ $pool }} connections and one more while it starts:

  ({{ $serverPeak }} + {{ $schedulerPeak }}) x ({{ $pool }} + 1) = {{ $peakConnections }}

against a max_connections that defaults to 100. Lower config.databasePoolSize
before raising a replica count, or put a pooler in front and set
secret.directDatabaseUrl so migrations and the first-account claim go past it.
{{- if gt $peakConnections 100 }}

WARNING: {{ $peakConnections }} is past that default. Scaled all the way out, replicas will fail
to connect rather than queue. Raise max_connections to suit, or lower
config.databasePoolSize, or lower the replica ceilings.
{{- end }}
{{- if .Values.secret.existingSecret }}

Credentials come from the existing Secret {{ .Values.secret.existingSecret }}. Every key in it
is handed to the API and the scheduler as an environment variable, so it must
carry DATABASE_URL and AUTH_SECRET, whichever of DIRECT_DATABASE_URL,
GOOGLE_CLIENT_SECRET, SMTP_USERNAME, SMTP_PASSWORD and SETUP_TOKEN apply, and
nothing else.
{{- end }}
